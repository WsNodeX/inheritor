一个 Agent Skill：找出代码里"没把话说清楚"的地方，补上。

## 它针对的问题

能跑的代码，不等于能自己解释的代码。这个差距在写的时候看不见，在读的时候很贵：

```python
if len(batch) > 1000:          # 为什么是 1000？
    flush()

MAX_BATCH = 1000               # 厂商文档写明单次写入上限；超过返回 413
if len(batch) > MAX_BATCH:
    flush()
```

凌晨三点读这段代码的人会问三件事：这原本想干什么、作者假设了什么、我下一步该看哪。
第一版一个都答不上来。

## 快速开始

```bash
git clone https://github.com/WsNodeX/inheritor ~/.claude/skills/inheritor
```

然后对着代码说：`用 inheritor skill 处理 src/。`

或者直接跑检查器：

```bash
python scripts/inheritance-check.py --path src/
```

## 八条规则

| # | 规则 | 判定失败 |
|---|---|---|
| 1 | 按搜索框命名 | 你 grep 这个名字，落不到对的地方 |
| 2 | 注释回答 why | 注释是下一行代码的慢速复制 |
| 3 | 每个数字都有来源 | 一个字面量决定行为，却没人说谁定的 |
| 4 | 错误必须可行动 | 只说失败了，不说下一步查什么 |
| 5 | TODO 必须有解除条件 | 没人知道什么时候能删 |
| 6 | 每个模块给一张地图 | 读的人找不到入口在哪 |
| 7 | commit 说 why | 消息在重复 diff |
| 8 | 不留隐式契约 | 函数假设了一件事，但从没写下来 |

规则 1、3、4、5、8 可机器检查，已实现。规则 2、6、7 需要判断力，
`references/patterns.md` 用前后对照覆盖。

## 它不会做什么

**不会给每个没 docstring 的函数报警。** 早期版本这么干，在一个健康的代码库上报了
41 条——狼来了的工具没人用。现在规则 6 只在"公开函数 + 两个以上无类型注解的参数"
时才触发。

**不会叫你加注释。** 复述代码的注释比没有更糟：它一边腐烂一边显得权威。规则 2 的
修法通常是换个更好的名字。

**不会重构能跑的代码。** diff 是评审单位。

## 为什么做这个

大部分代码质量建议在优化**代码**。这个在优化**读者**。

两者经常冲突：一个名字诚实的巧一行，胜过一个没人看得懂的六行展开。最有价值的规则
是第 3 条——一个没有解释的字面量，是一个把理由删掉了的决定，而这是代码库遗忘"自己
为什么能跑"最常见的方式。

## 局限

- **目前只支持 Python。** 检查器用 `ast` 和 `tokenize`；规则本身的文字部分与语言无关。
- **找不回从没被记录的意图。** 如果某个常量的理由只存在于某个被删掉的聊天记录里，
  检查器只能告诉你它没被记录，不能告诉你它是什么。
